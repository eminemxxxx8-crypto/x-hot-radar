# x-hot-radar

免费的名人事件线索雷达：Google News RSS / Google Trends → Python → GitHub Actions → 现有 Telegram Bot。

它帮助发现值得关注的报道，**不直接监测 X，不知道 X 转发量、曝光量或真实传播速度，也不能自动证明新闻属实**。没有接入 AI、付费 X API 或其他收费服务。

## 本次改进

- 中英文重点人物查询加上演员、歌手、球星等开放事件查询。常见姓名映射用于归一化；名单外的人物可由带职业称谓的标题进入，仍受可信来源和事件条件约束。
- 以报道发布时间 120 分钟为基本窗口，优先新报道；过滤回顾、旧闻重提、赛前稿、意见和明显假设标题。RSS 时间不是事件发生时间，消息会明确区分。
- 根据媒体域名识别来源，合并同媒体不同域名、相同标题、明显通讯社转载。普通争议、传闻需要至少两个不同媒体组刊载，且至少一个在可信媒体表中；45 分钟内的可信媒体具体进展可先报，始终标注“尚未独立核实”。没有来源元数据的条目不推送。
- 按人物、主题线索和词面相似性聚合事件；同一事件同一阶段只报一次，公开回应、道歉、品牌解约、被捕、起诉、判决可以成为后续进展。同一个人的不同事件可以连续提醒，取消原有的 8 小时人物/类别冷却。
- 用新鲜度、不同媒体组数量和**具体关联标题**进入 Google Trends 的信号排序。Google Trends 只作辅助，不能单凭一个人名上趋势就推送；这不是 X 热度或增长率测量。
- 消息使用 Telegram HTML，将长链接隐藏在可点的媒体名称里；保留来源标题，附简短中文分类和发帖角度。英文标题保留原文，避免免费规则假翻译出事实。
- 每次 Telegram 接受消息后立即保存状态，后续消息失败也会尝试提交已成功的记录。写入状态采用临时文件替换，损坏状态会停止运行，不会静默清空历史。

## 本地开发与测试

Python 3.12，无第三方运行依赖。

```bash
python3 -m unittest discover -s tests -v
python3 radar.py --help
python3 radar.py --dry-run
```

`--dry-run` 不调用 Telegram、不改写磁盘状态。`--state /tmp/radar-state.json` 可指定独立状态文件。新的空状态或旧版状态的首次成功采集会安静建立基线，因此第一次预览可能没有输出；可从日志的 `baseline` 和 `candidates` 判断，不能把无预览等同于无抓取。

本次本地回归使用合成 RSS 和模拟 Telegram，覆盖 41 项测试；没有向真实聊天发消息。云环境在线 RSS 被代理 403 阻止，不能把这些测试当作线上抓取或真实 Telegram 排版验收。工作流可通过 actionlint 1.7.7 静态检查。

## 部署（审核 PR 后再合并）

1. 审核改动并合并到默认分支 `main`。不需要新建 Bot，也不需要重新创建已存在的 `TELEGRAM_BOT_TOKEN`、`TELEGRAM_CHAT_ID` GitHub Secrets。本项目不读取密钥内容。
2. 保留现有 `data/state.json`。新版首次运行会将旧哈希迁移到 v2，并静默记录当前批次，避免升级后一次性重发。此轮也可能略过刚发生的消息，这是迁移的取舍；不要为了“初始化”删除历史。
3. 在 Actions → **X Celebrity Hot Radar (free)** → **Run workflow**，选择 `main`，保持 `send_test=false`。首次运行应看到建立基线及状态提交，随后根据事件发送通知。只有明确想收到测试消息时才选 `send_test=true`。
4. 查看日志中的源数量、`candidates / events / eligible_updates / alerts / baseline`，以及 Summary 的上次成功采集间隔。无提醒可能是没有合格的新事件，不等于未执行；应看 Actions 运行列表。
5. 保留 Actions 的仓库内容写权限。分支保护若禁止 Bot 写 `main`，状态提交会失败，需要按仓库规则允许状态持久化；不要通过强制推送处理。提交冲突也会明确失败。

PR 和代码 push 只跑无密钥测试，不发消息。定时/手动生产任务仅在 `main` 执行；推送有串行锁，运行时重新检出 `main` 读取最新历史。默认每轮最多两条，后续合格事件可在窗口内下轮补发。

## 免费运行与调度边界

计划改为每小时第 **7、17、27、37、47、57 分钟**，即每 10 分钟尝试触发；没有用长时间 sleep 或不断运行的轮询占用免费 runner。当前是公开仓库，使用标准 Linux runner。若以后转私有仓库，要检查 Actions 免费分钟额度和预算：每天理论 144 次，每次有测试与运行两个 job，计费按 job 向上取整，可能超出免费额度；本项目不启用付费额度或外部服务。

**修改 cron 不保证修复 GitHub 调度稀疏。** 平台可能延迟甚至丢弃排队任务；定时只读取默认分支；公开仓库 60 天无活动还可能停用定时任务。可以手动 Run workflow 补查，但缺失的过去时段无法靠 RSS 完整回补。实测和排查方法见 [调度诊断](docs/scheduling.md)。

## 内容与去重的边界

- “可信媒体”是可审查的域名规则，不是对报道事实的认证。多个媒体可能同源转载；代码只识别相同标题、同媒体组和显式通讯社标记，无法证明独立采访。传闻/指控、媒体报道、规则生成的个人评价分别标注。
- RSS 通常只有标题、链接和报道时间，无法可靠提取完整事实、事件发生时间和当事人原话。新发布的旧事件若没有回顾提示词，仍可能漏判；重大新进展标题若同时带回顾词，也可能被保守过滤。
- 事件聚合是可解释的规则，不是通用语义理解。无共同主题词的改写、中英文异名可能漏合并；同一个人 72 小时内两个相似主题事件也可能误合并。事件历史保留 72 小时，原始标题哈希最多 4000 条；更久之后大幅改写的旧事件仍可能重现。重要性、中文用户熟悉程度也只能近似判断。
- 名单外识别要求“职业＋人名”的可识别形式，不能穷尽明星；来源表外的地区媒体可能导致漏报。宁可少报，也不把任意姓名或媒体数包装成“全网爆火”。
- 发帖角度是按事件类别生成的**规则草稿和个人评价**，没有自动阅读正文、可靠翻译或高质量观点创作能力。它可能重复，需打开报道核实、自己改写，不能保证每条都像真人原创。本项目不会假装接入 AI 模型。
- Telegram `sendMessage` 没有本项目可用的幂等键：若服务端已接收但响应超时，或 runner 在接收后、保存前终止，仍可能下次重复。代码不盲目重试发送；若状态无法推回仓库，也不能承诺恰好一次投递。
